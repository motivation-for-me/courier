
# SwiftLog QA audit

Date: 2026-09-30

## Authoritative product baseline

- One courier company administrator performs normal business administration.
- Staff can manage permitted company operations and may also be enabled as riders.
- Shop managers are linked to one shop and can create/view only that shop's shipments and documents.
- Shops are senders and may have pickup addresses.
- Shipment creation creates the record and CN; pickup remains a separate physical event.
- A rider sees only assigned work, can scan a QR as an optional shortcut, confirms pickup, starts delivery, fails delivery, or completes delivery.
- The active city workflow does not depend on hubs, manifests, transit, projects, OTP, or rider PINs.
- Admin corrections require an audit reason. Historical tracking and audit records must remain intact.

## P0: data integrity, security, and blocked core workflows

1. **Pickup completion contradicts the current rider UI.** The API requires a prior `dispatch.cn_scanned` audit record, but the rider UI offers direct `Confirm pickup`. This produces a predictable Bad Request unless the rider scanned first, contrary to the requirement that QR is optional.
2. **Delivery completion leaves the rider assignment ACTIVE.** `DeliveryService.complete` marks the consignment delivered but does not end its active assignment. This creates stale relationships and can prevent rider removal or access changes.
3. **Delivery status completion has two competing code paths.** `/delivery/:id/status` and `/delivery/:id/complete` implement overlapping delivery logic with different COD, attempt, assignment, and idempotency behavior.
4. **Client-generated idempotency keys are not retry-stable.** The completion request uses `Date.now()`, so a retry creates a new key instead of safely replaying the original command.
5. **Login is ambiguous across organizations.** Users are unique by `(organizationId, email)`, but login searches by email alone with `findFirst`. The same email in multiple organizations can authenticate unpredictably.
6. **Public tracking uses the database UUID as its detail key.** The QR URL exposes the consignment primary key and treats it as the PII-access secret. A dedicated random, rotatable public tracking token is required.
7. **Public event remarks are returned without a public-safe projection.** Internal operational remarks can leak through unauthenticated tracking.
8. **Authorization capability names do not match mutations.** Staff create/update/delete and branch create/update/delete controllers use read permissions such as `user:view` and `route:view`; service-level ADMIN checks reduce exposure today but the policy is internally inconsistent and unsafe to extend.
9. **Database migration state is not verifiable.** Only a small set of recent migrations exists for a large schema, while `prisma migrate status` currently fails against the configured database. Production reproducibility is not established.
10. **No automated tests protect authorization or lifecycle rules.** The repository has no test scripts or test files for organization isolation, rider assignment, pickup, COD completion, status transitions, document access, or public tracking privacy.

## P1: essential courier functionality gaps

11. **Rider completed-history is absent.** Delivered jobs disappear from `me/assignments`, and “Completed today” is not backed by API data.
12. **Rider failure capture is inadequate.** A shared optional remarks field is used for all parcels; failure reason is not required or captured per delivery attempt in the direct rider flow.
13. **COD completion uses a native browser confirmation.** It does not provide a controlled amount-entry/confirmation state, payment method context, or an accessible inline error.
14. **Proof of delivery is absent.** There is no recipient name confirmation, signature/photo evidence, delivery timestamp review, or configurable proof policy.
15. **Rider navigation/contact actions are absent.** Assigned work shows limited address data but lacks one-tap call, map/navigation, landmark visibility, delivery instructions, and COD summary on the actionable card.
16. **Assignment scheduling is incomplete.** Workload and area recommendations exist, but there is no route order, scheduled time/window, manual priority, availability calendar, or reassignment reason in the UI.
17. **Notifications are not operational.** A notification abstraction exists, but shipment-created, rider-assigned, out-for-delivery, failed, and delivered customer notifications are not implemented end to end.
18. **Admin correction UX uses a generic fixed reason.** Status correction sends `Changed by administrator` instead of requiring the actual reason and confirming the impact.
19. **Admin can choose legacy/impossible statuses from the active UI.** The dropdown exposes states outside the simplified workflow and can produce misleading histories through the correction endpoint.
20. **Shop creation and shipment creation are not atomic.** A new shop/address can remain orphaned when shipment creation fails.
21. **Multiple pickup addresses are modeled but the shipment form silently uses the first.** This is acceptable only while the one-address policy is explicit and enforced; currently it is implicit.
22. **Deletion semantics are surprising.** Deleting a shop soft-deletes all of its active consignments and disables projects. The UI does not preview this impact or require a typed/descriptive confirmation.
23. **Operational updates are inconsistent about audit records.** Several reference-data updates/deactivations do not record the same before/after audit detail expected from shipment commands.
24. **Refresh sessions do not rotate.** Refresh returns a new access token but reuses the same refresh token/session, increasing replay exposure.
25. **Access-token revocation is delayed.** The auth guard trusts JWT claims until expiry and does not check current user/session state on each request; permission removal can remain usable for up to 15 minutes.
26. **List APIs lack a consistent pagination contract.** Some queries have hard limits, while customer, rider, staff, branch, and consignment workflows do not expose a shared cursor/page shape suitable for growth.

## P1: frontend reliability and UX defects

27. **The animated rider depends on `localhost:4173`.** Login and loading visuals require a separate Python server and will fail in production or on another device.
28. **QR detection depends on the browser-only `BarcodeDetector`.** Unsupported browsers receive only a manual CN fallback; there is no bundled cross-browser scanner.
29. **Error and success presentation is conflated in the rider view.** Some failed requests render in success styling because one message string carries both states.
30. **Duplicate legacy components remain in the active bundle.** `LegacyHeader`, `LegacyBooking`, placeholder workspaces, and a second rider return path increase confusion and regression risk.
31. **Visible source text contains encoding corruption.** Examples include malformed plus signs, ellipses, arrows, and dashes in UI copy.
32. **Several controls are visually present but non-functional.** Legacy filters, exports, placeholder dashboard metrics, and API-integration panels can appear actionable without complete behavior.
33. **PDF preview relies on opening a blank tab before fetch.** Pop-up policies and slow responses can produce confusing blank tabs; an in-app preview/download state is needed.
34. **Loading is globally blocking.** The bike loader covers the entire viewport for ordinary data loads instead of preserving page context with local skeletons.
35. **Mobile rider flow lacks a completed tab/history view.** Active actions improved, but there is no explicit Active / Pickup / Completed navigation or job detail sheet.
36. **Accessibility coverage is absent.** There is no automated keyboard, focus-trap, screen-reader, color-contrast, reduced-motion, or camera-dialog test.

## P2: model and maintainability debt

37. **The documented business model is obsolete.** It still declares Super Admin, hub managers, manifests, transit, OTP, and a network lifecycle as authoritative.
38. **Legacy modules remain registered and callable.** `Hub`, `Manifest`, `ManifestItem`, transit APIs, project APIs, OTP tables, legacy statuses, and related fields remain active despite not belonging to the corrected primary workflow.
39. **Legacy database relations remain widespread.** `hubId`, `currentHubId`, `projectId`, manifest relations, OTP relations, and their indexes prevent a simple model and increase migration/testing cost.
40. **Branches are still a first-class API/schema concept despite the current single-company-location decision.** This needs a controlled compatibility decision before removal, because existing users, riders, consignments, and manifests reference it.
41. **Status vocabulary contains two workflows.** `DRAFT/CONFIRMED/ASSIGNED_TO_RIDER/...` coexists with `BOOKED/VERIFIED/MANIFESTED/IN_TRANSIT/RECEIVED/...`, making rules and reporting ambiguous.
42. **Service type is an unconstrained string.** Invalid or inconsistent service names can enter the database and break reporting.
43. **Party and address kinds are unconstrained strings in the database.** DTO validation helps only API writes; database-level invalid values remain possible.
44. **Monetary and measurement constraints are incomplete at database level.** Non-negative and currency/business invariants rely mostly on DTO validation.
45. **Large frontend components are monolithic.** Rider, auth, shell, legacy booking, and navigation behavior share one file, making responsive and state regressions likely.
46. **Global CSS contains repeated breakpoint layers and overrides.** Multiple definitions for the same shell, page, metric, and mobile rules make final behavior order-dependent.
47. **No linting or formatting command is configured.** This contributes to one-line components, dead code, duplicate rules, inconsistent copy, and difficult reviews.
48. **Operational observability is missing.** There are no request IDs, structured request logs, actor-aware error logs, latency metrics, or health checks for database readiness.
49. **No deployment smoke test exists.** Port conflicts, CORS origin mismatch, API reachability, animation asset availability, and database connectivity are discovered manually.

## Controlled legacy dependency audit

Deletion is not authorized yet. Current references confirm that these cannot be dropped safely in one migration:

- `Hub`: referenced by users, consignments, tracking events, branches, manifests, transit service, auth claims, permissions, docs, and indexes.
- `Manifest` / `ManifestItem`: referenced by active Nest modules/controllers/services, consignment relations, branches/hubs, permissions, statuses, and documentation.
- Transit fields/APIs: referenced by the registered Transit module, tracking events, consignment current-location fields, permission codes, and documentation.
- `Project`: referenced by customer APIs, consignment create/read relations, customer deletion, frontend API types, permissions, indexes, and documents.
- `OtpChallenge`: currently schema-only in the inspected active application code, but referenced by User and Consignment relations and obsolete documentation.
- Legacy statuses: referenced by schema enums, manifest/transit services, admin UI status options, status styling, docs, and historical rows.

## Engineering order

1. Fix pickup, delivery completion, assignment closure, COD, idempotency, and rider history.
2. Harden authentication, public tracking privacy, and mutation permissions.
3. Add lifecycle and authorization integration tests before further structural work.
4. Complete rider job details, failure/POD handling, contact/navigation, completed history, and notifications.
5. Remove dead frontend paths, encoding errors, fake controls, and the external loader-server dependency.
6. Reconcile documentation and implement a controlled legacy schema migration only after database record counts, API/frontend references, reports/documents, and historical retention are verified.
7. Add CI, linting, accessibility checks, deployment smoke tests, and observability.
